# Billing security review (Stage 6)

Scope: everything on branch `feature/razorpay-billing-trial` from Stages 1 to 5, reviewed on 2026-11-08 against head `530ee3e` plus the Stage 6 changes. Method: reading the code and SQL, static guard tests, targeted failure-injection tests, and scans of the built frontend and API bundles. **Nothing was run against live Razorpay or the production database** (no Test Mode keys). Findings that depend on real Razorpay behaviour are marked BLOCKED, not assumed.

**Result: no critical or high findings.** Two medium defects were found and fixed in code (S6-01, S6-02). Remaining mediums are either fixed in the repo but need one owner action in GitHub (S6-03) or are deployment requirements and residual risks that are documented below.

Ratings: critical = money or data loss or account takeover reachable by an outsider; high = same but needs a precondition that is realistic; medium = limited impact or needs operator error or an unusual precondition; low = hygiene; info = checked, nothing to do.

## Findings

| ID | Rating | Finding | Status |
|---|---|---|---|
| S6-01 | medium | **Concurrent "start subscription" calls could create two Razorpay subscriptions.** A second request saw the first request's in-flight `creating` row, assumed an earlier attempt had died, retired it and created another subscription at Razorpay. The database unique index and the orphan cancel kept the end state at one live subscription (no double billing), but it cost extra Razorpay calls and could strand a mandate for a moment. | **Fixed** in `service.ts`: a young `creating` row (younger than `max(60 s, 3 x Razorpay timeout)`) now answers 409 `subscription_in_progress`; only an old one is retired. Tests: `stage6.test.ts` (concurrent calls create exactly one; a crashed attempt still heals). |
| S6-02 | medium | **A mistyped `BILLING_ENFORCEMENT` silently left the gate off** (fail-open by design, so a typo cannot lock everyone out) with no log line at all, so an operator who meant `on` would believe AI routes were gated. | **Fixed.** Value is case-insensitive and trimmed (`ON`, ` On `). Any other value still means `off`, but now logs `billing_enforcement_invalid` at startup. Tests: `stage6.test.ts`. |
| S6-03 | medium (low for a repo with one writer) | **Reconcile workflow secrets.** A repository secret can be read by a workflow run from any branch by anyone with write access (`workflow_dispatch` on a branch whose copy of the file is edited). The job holds the service-role key. | **Fixed in the file, owner action needed:** job now has `environment: billing-reconcile` and a `github.ref == 'refs/heads/main'` guard. In GitHub: create the environment `billing-reconcile`, set *Deployment branches* to `main` only, and move the eight secrets from repository secrets into that environment. Guard test: `billingSecurityGuards.test.ts`. Residual (low): third-party actions are pinned by tag, not commit SHA; package code (razorpay, supabase-js, axios) runs with the secrets, as it does in production. `npm ci --ignore-scripts` limits install-time code. |
| S6-04 | medium | **Webhook rate limit runs before the signature check and is per IP.** If `TRUST_PROXY` is not set on Vercel, every caller shares the proxy's address and one flood could use up the 120/min bucket and delay genuine webhooks. Impact is delay only: Razorpay retries, and the reconciler re-reads state. No integrity impact. | **Mitigated, deployment requirement:** set `TRUST_PROXY` correctly for Vercel (the app already needs this for its own limits) and keep the shared Redis store (the production default). Verify in the preview test (checklist in the Stage 7 report). |
| S6-05 | low | **`x-razorpay-event-id` is not covered by the signature.** An attacker who captured a valid signed body could replay it with a new event id and get it processed again. Harm is nil: the handler writes Razorpay's fetched state (not the body's claim) and payments dedupe on the payment id. Cost is one extra ledger row. | **Accepted, tested** (`stage6.test.ts`: replay under a new id converges, one payment row, a replay cannot undo a later cancel). Capturing a signed body also needs a TLS break. |
| S6-06 | medium | **CSP widened for Checkout:** `script-src` gains `https://checkout.razorpay.com` (a third-party script, no subresource integrity possible) and `frame-src` gains two Razorpay origins. `connect-src`/`img-src` origins that Checkout may need are unverified. | **Accepted, narrowed, guarded:** only those two directives, only those origins; no wildcard, no `unsafe-inline`/`unsafe-eval`; the loader script is injected only from the billing screen. Guard tests: `billingSecurityGuards.test.ts`, `billingClientGuards.test.ts`. BLOCKED: real-browser check in a preview deployment with Test Mode keys. |
| S6-07 | medium (residual) | **Trial abuse.** One trial per account and per normalised confirmed email (case, `+tags`, Gmail dots, googlemail). A person with several real mailboxes can still get several trials; the same card or UPI handle is not deduplicated across accounts (no payment-instrument fingerprint is collected). Every trial needs a verified email, a completed mandate and a Rs 5 debit, and AI usage keeps its daily quota, so cost per abuse is bounded to 3 days of quota-limited use. | **Accepted residual risk.** Mitigations already in place: email verification enforced by billing itself, claim survives account deletion, claim consumed only after Razorpay confirms the mandate. If abuse appears, a per-instrument check needs a product decision. |
| S6-08 | medium | **Webhook raw body on Vercel unproven.** If the platform hands the function a parsed body, the webhook answers `raw_body_unavailable` and processes nothing (fails closed). Integrity is safe; availability depends on the preview test. | **BLOCKED** (needs a Vercel preview plus a Razorpay test webhook). Fallback is the reconciler, which already re-reads Razorpay state. |
| S6-09 | low | **Deleting a user outside the app** (Supabase dashboard, Auth admin API) bypasses the `delete_own_account()` gate. A live orphaned subscription is cancelled by its next webhook, so at most one charge can happen before the cancel. | **Accepted, operational rule:** delete users through the app, or cancel the subscription first. Orphan handling is tested end to end (`stage5.test.ts`). |
| S6-10 | medium (revenue, not security) | **Access after recovering from `halted` may cover a cycle that was never paid** (Razorpay does not charge invoices generated while halted). | **BLOCKED + owner decision** (accept, or require the next successful charge). Not changed here. |
| S6-11 | low | **Logger scrubbing did not recognise an HTTP Basic credential or a Razorpay key id inside free text.** Razorpay authenticates with Basic `key_id:key_secret`. Billing code never logs error text (names, codes and ids only, proven by tests), so this was defence in depth for the generic `unhandled_error` path. | **Fixed** in `logger.ts` (`Basic [redacted]`, key ids redacted). Test: `logger.test.ts`. |
| S6-12 | info | **Service-role confinement.** `SUPABASE_SERVICE_ROLE_KEY` is read only by `billing/config.ts` (and the pre-existing video-library scripts); the service-role client is built only in `billing/store.ts`; the store is constructed only from `billing/routes.ts` and `scripts/billing-reconcile.ts`. Every store method that takes a user id filters on it; id-less methods are reachable only from signature-verified or Razorpay-confirmed paths. | **Pass**, pinned by `billingSecurityGuards.test.ts`. |
| S6-13 | info | **Secret exposure.** Built frontend bundle scanned for secret names, key-shaped literals and server-only identifiers: none. Committed API bundle: no key-shaped literal. No `VITE_` variable for any payment or service-role value; `.env.example` clean. No billing response contains a secret (`routes.test.ts`); no log line does even when dependencies throw secret-bearing errors (`stage6.test.ts`). Store errors carry an operation name and SQLSTATE only. Razorpay errors are reduced to a kind and a safe upstream code. | **Pass.** |
| S6-14 | info | **Webhook handling.** Raw bytes only (anything else fails closed), HMAC compared in constant time, nothing touches the database before the signature verifies, body capped at 256 kb, content type fixed, per-IP limit, idempotency through `billing_begin_webhook_event`, stored as a SHA-256 digest never the body, state taken from a fresh Razorpay fetch, terminal states never regress. | **Pass** (live raw-body behaviour: see S6-08). |
| S6-15 | info | **Authentication, isolation, RLS.** Every `/api/billing/*` route except the webhook sits behind the verified-JWT pipeline; identity comes only from `req.user`. Clients can read only their own subscription and payment rows, see no Razorpay ids or internal columns, and can write nothing (including self-granting paid status). Trial claims and webhook events are invisible to clients; billing functions are service-role only; `delete_own_account()` refuses (`BL001`) until Razorpay confirms the stop. | **Pass** (`rls.billing.test.ts` on PGlite, `routes.test.ts`, `stage5.test.ts`). |
| S6-16 | info | **Default behaviour.** `BILLING_ENFORCEMENT` defaults to `off`: AI routes stay ungated until the owner turns enforcement to `shadow`, then `on`, as a separate approved production step. Billing routes answer a safe 503 while billing is unconfigured; every other route is unaffected. | By design. |

## What was not verified

Anything that needs real Razorpay or a real browser: the INR 5 refund timing and field, the authorization amount for UPI Autopay and eMandate, `subscription_card_change` in Checkout, API cancellation of `pending`/`halted`/`created`, `total_count` limits, the webhook raw body on Vercel, CSP origins Checkout really needs, and the halted-recovery access question. The test-mode checklist for each is in the Stage 7 report.
